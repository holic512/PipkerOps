# Redis 会话与节点监控改造计划

日期：2026-11-06。状态：主链路已实现；Linux 真实集成与规模验收待执行，见 DEVELOPMENT.md 本次记录。

## 已确认范围

- 浏览器 Session 从 PostgreSQL 迁到 Redis；切换后现有登录统一失效，重新登录。
- 节点监控覆盖 CPU/负载、内存/Swap、磁盘/inode、网络/连接、磁盘 IO、进程、systemd 服务及容器。
- 同时改善采集新鲜度、接口响应、传输体积和页面展示，不只调整刷新频率。
- API Key、用户、角色、任务、审计和历史指标继续由 PostgreSQL 持久保存。
- 本文只规定实施方案和验收，不启动进程、不修改线上节点、不执行数据库迁移。

## 代码核对结果

1. 登录通过 `db().session.create` 创建固定 8 小时会话；请求鉴权、退出和 Gateway 活动终端复核均依赖 Session 表，Worker 清理过期行。没有滑动续期。
2. Agent `monitor` 每 15 秒发送心跳并运行一次 Collect。CPU、文件系统、进程、连接、systemd、Docker 顺序采集，整次采集共用 10 秒超时；Docker 和 systemd 各有 3 秒子超时。首轮是立即启动采集，并不是固定等待 15 秒。
3. Web 通用查询默认每 15 秒刷新，设备历史每 30 秒刷新。叠加采集等待和下一次轮询，用户看到数据可能明显滞后；实际各段耗时仍需测量。
4. 节点详情调用 nodes.list，再从全部节点中查找当前节点；每个节点附带最新完整 payload。CPU/内存之外的很多信息只在“采集详情”JSON 展示。
5. Gateway 按节点串行处理消息；指标接收涉及节点校验、更新时间、写样本、写元数据及旧 Deployment 状态更新。需要测量这些步骤是否挤占终端、日志和心跳处理。
6. Gateway 指标验证要求 CPU 和内存同时有效；任一缺失可能导致其他有效指标整包不被保存，甚至触发连接错误处理。
7. 当前最新采样查询已在 SQL 内逐节点 LIMIT 1，历史查询也有分桶上限。应保留这些优化，不能把所有慢归因于“查询了全部历史”。
8. 网络、IO 累计计数及设备身份已经存在；当前进程只有有限 PID 样本及名称/内存百分比，不是真正的 CPU Top 排行。部分内存、网络、IO 明细已经采集，需整理而非重复采集。
9. 恢复流程会清理 pko:* Redis 键。新会话和实时缓存纳入此命名空间，恢复后不得复活旧登录。

## 第一阶段：建立性能和指标基线

先在隔离环境记录 1/10/50 节点场景，并对获准的真实节点作只读测量。将页面“加载慢”与“指标更新慢”分开。

- Agent：每类采集耗时、总耗时、超时次数、序列化大小、截断项及失败原因。
- Gateway：收到帧至处理完成的耗时、指标队列深度、写库耗时、心跳/终端等待时间。
- Web：nodes.list、单节点查询、短/长历史的 p50/p95、SQL 次数、返回字节及页面可用时间。
- 链路时间：sampledAt、采集耗时、receivedAt、servedAt；单机性能用单调时钟，跨机时间需考虑时钟偏差。
- 测试数据覆盖真实设备数量和 payload 体积；明确固定测试硬件、并发用户数和数据窗口。

输出基线表、慢查询执行计划和指标字段盘点，作为后续前后对比依据。不用单次请求或单节点测试外推生产 SLA。

## 第二阶段：Redis Session

### 存储与授权

- 新建统一服务端 session-store，提供 create/get/revoke/revokeUser；所有调用点通过该入口读写。
- 浏览器继续保存随机 token；Redis key 使用 pko:session:<tokenHash>，不保存原始 token。
- Actor.sessionId 使用摘要身份定位 Redis 会话；记录 userId、createdAt、expiresAt、存储格式版本。
- 使用原子 SET + TTL，固定有效期保持 8 小时，Cookie Max-Age 与服务端过期时间一致；读取同时检查绝对过期时间。
- 用户与角色仍以 PostgreSQL 为准；第一版鉴权读取 Redis 会话后查询当前用户，避免角色快照过期或已删除用户继续访问。因此迁移消除 Session 表访问，不承诺所有鉴权都不访问数据库。
- 如维护用户会话索引，使用带过期时间的有序集合，原子更新并清理过期成员，避免无限增长。支持全用户吊销并验证并发登录语义。
- Redis 命令设置有界超时。Redis 不可用返回 503；会话不存在/过期返回 401。终端复核失败应停止授权，不能默认为有效。
- 保持 HttpOnly、SameSite、HTTPS/Secure、同源检查、登录限流和审计行为。

### 切换与清理

- 同步替换 login、logout、authenticate、refreshActor；移除 Worker 的数据库会话清理。
- Web/Gateway/Worker 协调切换并重启；仅 Redis 会话被认可，旧数据库登录统一失效，不双读、不把旧会话自动导入 Redis。
- 先停止使用 Session 表；稳定验证后以单独迁移移除 Session 模型/表和 User.sessions。明确升级与回退都需要重新登录。
- 替换集成测试中直接插入 Session 表的夹具，使用会话服务或真实登录。
- 系统备份不包含 Redis 登录态；恢复清理新 Session、票据和实时缓存。审计保留在数据库中。

### 验收

- 登录、退出、固定过期、多端登录、重复退出、用户删除/角色变化、Redis 中断恢复。
- 退出/失效后活动 PTY 关闭；撤销不受 Redis Pub/Sub 丢事件影响，仍定期复核。
- 多 Web/Gateway 实例读取一致会话；备份恢复后旧 Cookie 无效。
- 运行时不再调用 Prisma Session；API Key 的 scope、节点和高危授权保持原契约。

## 第三阶段：拆分节点实时与历史链路

### Agent 采集分层

| 层级 | 默认周期 | 内容 |
| --- | --- | --- |
| 心跳 | 10 秒 | 连接存活、Agent 版本；独立于采集任务 |
| 快速指标 | 5 秒 | CPU、负载、内存、Swap、网络累计计数、IO 累计计数 |
| 设备容量 | 15 秒 | 挂载点容量、inode，避免慢挂载阻塞快速采集 |
| 明细快照 | 15–30 秒 | 进程 Top、连接摘要、Docker/systemd 状态 |
| 静态信息 | 接入时及 10 分钟 | 系统发行版、内核、CPU 型号/核数、内存总量、设备属性 |

- 周期集中配置并限制上下界，首轮尽快采集。实际默认值经基线确认；同一类不允许采集重叠。
- 采集采用有界并发和分类超时；任何慢项只影响自身。单个设备权限/挂载故障不使其他指标失效。
- CPU、进程、网络、IO 通过连续计数差计算；首次基线不伪造速率。明确进程 CPU 多核百分比口径。
- 快照携带 schemaVersion、bootId、序列、采样区间、各类时间、采集状态和截断信息；重启/乱序/旧连接数据不能覆盖新结果。
- 限制设备、进程、连接、容器数量和帧大小；暴露 limit/returned/total 或 truncated，不静默宣称全量。
- 权限不足/不支持/超时/尚无基线分开表示；不把失败填成 0，也不因一个字段失败断开正常管理连接。

### 实时数据、历史及消息处理

- Redis 保存各节点最新有效摘要和分类快照，按节点与类别组织；TTL、sampledAt、receivedAt 和 freshness 独立记录。
- 在线状态与指标新鲜度分开。节点在线但某类指标超时，页面显示该类过期；不能因为缓存键存在就判断在线。
- Redis 不可用时从 PostgreSQL 的最新历史/快照读取并明确标记过期；不回退为“浏览器实时访问 Agent”。历史写入不因缓存异常停止。
- 实时更新默认 5 秒；历史仍按约 15 秒保存，保持现有原始 30 天、摘要 365 天策略，不把数据库写入量直接翻三倍。
- 新的历史采样保留必要数值和设备计数，不在每次样本中重复完整进程、端口、服务清单；明细当前快照单独保存。旧 payload 可继续读取。
- 核心标量使用类型化可空字段；设备维度延续按节点/设备/方向的模型，扩展数值和小时聚合。进程/连接只保存有界当前快照；本轮不提供无限维度逐进程一年历史。
- 定义每个新指标的单位、均值/峰值/差分/加权聚合口径。CPU/内存部分失败需同步改可空字段、SQL、告警和 MCP schema，不能只放宽接收验证。
- 指标接收与数据库/旧 Deployment 更新解耦，队列有界并合并过时实时帧；任务日志、结果和 ACK 不得丢弃或套用指标丢帧策略。
- 重连先显示最近快照并标明时间，历史曲线保留真实缺口。Redis 最新快照不作为资源操作身份或任务事实来源。

### 查询和浏览器更新

- 新增单节点信息、实时摘要、分类明细入口；节点详情不再获取全部节点的完整 payload。
- 节点列表只请求身份、在线状态和紧凑指标；旧 nodes.list/MCP 契约在兼容期保留，新界面使用轻量入口。
- 当前标签按需请求明细；未打开的进程、容器、服务与历史面板不持续查询。
- 采用一个页面级 SSE 连接接收“小型变更通知”，合并通知后通过 SWR 定向刷新；不为每个面板建立连接，不在通知里广播完整敏感快照。
- SSE 在服务端按角色、scope 和节点范围过滤，定期复核 Redis 会话及用户权限；Session 过期关闭连接。独立订阅连接，不让 Redis 订阅模式占用普通命令客户端。
- SSE 重连执行一次完整授权刷新，使用有界轮询兜底；Pub/Sub 只作通知，不依赖事件历史保证数据完整。
- 页面隐藏暂停非必要查询，切回立即刷新；历史刷新独立于实时指标，避免每 5 秒重算一年历史。
- 动态授权响应禁用共享 HTTP 缓存；配置 SSE 代理禁用缓冲、保活和断线清理。

## 第四阶段：补齐指标与可用页面

| 类别 | 指标范围 | 展示与历史 |
| --- | --- | --- |
| 系统信息 | 发行版、版本、内核、架构、启动时间、运行时长、虚拟化、Agent 版本、采集状态 | 信息区与状态；不对静态字段反复建历史 |
| CPU/负载 | 型号、逻辑/物理核数、总/各核使用率、user/system/idle/iowait/steal、load 1/5/15、归一化负载 | 总览和趋势；各核有界明细 |
| 内存/Swap | total/used/available/free、buffers/cache、使用率，Swap 总量/使用/换入换出 | 容量卡片和趋势；明确 Linux used/available 口径 |
| 文件系统 | 设备、挂载点、类型、total/used/free/available、使用率、inode 总量/使用/剩余、只读属性 | 设备表与容量/inode 趋势 |
| 网络 | 网卡/IP/MTU/链路状态、收发累计字节/包数、B/s、pps、错误、丢包、可获取的链路速率 | 网卡选择、趋势和错误状态；虚拟网卡速率不可得时标记不支持 |
| 连接 | TCP 各状态计数、UDP 概况、监听地址/端口及 PID | 汇总及有界明细；不高频传输完整连接表 |
| 磁盘 IO | 设备读写字节/次数、吞吐、IOPS、读写延迟、队列、忙碌时间 | 按设备趋势；基于增量计数并标明测量区间，NVMe 等多队列设备需说明 util 口径 |
| 进程 | 总数、状态分布、PID/名称/用户、CPU、RSS/VMS、内存占比、线程数、可获取的 IO | 按 CPU/内存排序的 Top 列表；不是截取前若干 PID 冒充排行 |
| systemd | 已加载服务及 active/sub/failed 状态、数量 | 状态汇总和筛选表；明细复用已有按单元查询能力 |
| 容器 | 运行/停止/异常数量、准确 ID/名称/镜像/Compose 归属、健康、重启次数、CPU/内存、网络/块 IO | 实时表；有界批量采集，不逐容器无限创建命令 |
| 采集质量 | 分类耗时、最后成功时间、失败原因、样本间隔、缺口和截断 | 页面可见的过期/部分失败提示 |

上述指标按 CPU/内存 → 磁盘/网络/IO → 进程/连接/服务/容器逐批交付，每批包含采集、契约、存储、展示和验证。硬件温度、SMART、GPU、eBPF 等额外依赖能力不作为本轮默认要求。

界面复用 DataTable、ViewTabs、QueryState、Status 和现有图表主题；需要扩展公共契约时同步 UI_COMPONENTS。新指标不能仅堆在 JSON 中，JSON 保留为诊断辅助。

## 验收目标与发布

以下为实施目标，尚无测试结果承诺：

- 固定隔离硬件与网络条件下，50 节点、5 个活动浏览器，轻量列表/实时摘要接口 p95 目标不超过 500ms（暖请求）；记录数据库和 Redis 故障时的差异。
- 快速采集 p95 目标不超过 1 秒；成功采样到浏览器更新 p95 目标不超过 2 秒。5 秒周期意味着快速指标通常应在约 8 秒内可见，不能把 2 秒传递目标误解成总数据年龄。
- 高成本/静态分类按自己的周期考核，并在页面显示时间；首次速率需两个样本，不承诺即时出现。
- 50 节点历史样本数维持约每节点 15 秒一条（约每日 28.8 万条），另测实际字节/设备摘要增长、CPU 和维护耗时。
- 断网、慢 Docker/systemd、只读/无权限、Redis 重启、部分字段失败、Agent 重启/设备替换/序号乱序均有真实测试。
- 保持历史窗口有界、UTC 分桶、加权速率、计数重置缺口、旧数据兼容和资源实例身份约束。
- 执行 lint、check、相关 TypeScript/真实 Redis/PostgreSQL 集成、Go race 测试、生产构建；按改动运行独立部署、备份恢复、Docker 和终端回归。
- 页面验收包含亮/暗主题、桌面/窄屏、键盘、加载/空态/过期/部分错误、会话退出后 SSE/PTY 释放。
- Linux/Node 24 作为完整验收环境；Windows 的平台依赖测试和沙箱网络 EACCES 单列，不混报为业务通过。

发布分两次主交付：先 Redis Session，再节点监控。第二次先部署兼容新旧采样的 Ops，再更新测试 Agent，验证后逐节点推广。已有协议字段不悄悄改变含义，旧 Agent 显示明确能力缺失。

每次提交递增实际受影响的 Ops/Agent 版本；代理配置、部署资源或 Skill 契约变化时，评估并同步递增部署脚本/Skill。同步 API、数据库、Agent、部署、开发验证和组件文档。

实施顺序：基线 → Redis Session → 单节点/轻量查询 → 分层采集与实时缓存 → 指标与历史 → SSE/页面 → 完整回归与发布。各阶段保留独立可审查的改动，第一阶段结果用于校准后续性能目标。
